# Walk City バックエンド設計書

## 1. この文書の目的

Walk City の Supabase バックエンドが管理するデータ、認証、歩数同期、ゲームロジック、権限制御を定義する。

コイン残高、建物配置、人口、土地開放、ランキングはバックエンドを唯一の正とする。
価格や効果値は設定データで管理し、ゲームバランス変更のたびにフロントエンドや関数を改修しない構造にする。
バックエンドのフレームワークは不要？RPCとSupabase Edge Functions (以下、「EF」)だけで十分？

とりあえず一人で追記修正していく方針。

利用するAIエージェント

- GitHub Copilot (コード補完 / VS Code)
- Google Gemini (学割特権の「Pro」モデルで)
- (できれば) Claude Code (Proプラン必須。コード検証等)

## 2. 技術構成

- Supabase Auth（Google ログイン。以下「Auth」と表記）
- Supabase PostgreSQL (以下「DB」)
- Row Level Security（RLS） (データ更新や表示の制限を行う)
- Supabase EF (Edge Functions。Google Health APIの連携 / 新しいユーザー登録)
- Google Health API（正式な API 名、認可方式、Web アプリから取得可能な歩数データは実装前に確認する）

Google Health 連携は EF 内のアダプターへ隔離する。利用する Google 側 API が変更されても、ゲームロジックとフロントエンドの契約へ影響を広げない。

歩数の取得はGoogle Health APIのstepsの項目からとる。

## 3. セキュリティのための設計プラン

- Googleのログイン、およびGoogle Health APIに利用する認可コード、アクセストークン、リフレッシュトークンは、SupabaseのEFのSecretsに保存する。DBテーブルには保存しない。
- SupabaseのRLSで、ユーザーが自分のプロフィール、街、歩数、コイン台帳を操作できるようにする。ユーザーは他人のデータを直接操作できない(公開するものは読み出しのみ可能)。
- EFは、Google Health APIの呼び出し、認可コードの交換、アクセストークンの更新を行う。DB関数は、コイン台帳、建物配置、人口計算などのトランザクションを行う。
- フロントでは外部APIの利用を行わず、必ずEF(以下、EF)を経由し、fetchが完了したらRPCを呼び出す。
- EFはGoogle Health APIの呼び出し中にDBロックを保持しない。(最悪デッドロックもあり)
- DB関数は、コイン台帳、建物配置、人口計算などのトランザクションを行う。

## 3. バックエンドの責務

- Google ログイン済みユーザーの識別
- プロフィールと街の初期作成
- Google Health の認可情報の安全な取り扱い
- 歩数の取得・日別保存・重複同期の防止
- 歩数からコインへの変換と付与
- 商業施設・工場によるコイン増加効果の適用
- 建物カタログ、価格、サイズ、効果の管理
- 建物・道路の購入、配置、移動
- マップ境界、土地開放、衝突、道路条件の検証
- 人口と役所効果の計算
- 全ユーザー人口ランキング
- 他ユーザーに公開する街データの提供
- RLS、入力検証、トランザクション、監査可能な台帳

## 4. 設計原則

### 4.1 サーバー権威

クライアントが送るコイン、人口、価格、建物サイズ、効果値、ユーザー ID を信用しない。
認証ユーザーとサーバー上のカタログ・街データから計算する。

### 4.2 原子的な更新

次の操作はそれぞれ一つのトランザクションで完了させる。

- 歩数の差分記録とコイン付与
- コイン減算と建物配置
- 建物移動と配置検証
- 土地開放条件の検証と開放状態更新

途中だけ成功する状態を作らない。

### 4.3 データ駆動の建物効果

建物の共通項目と効果を分離する。効果がない建物も空配列として扱い、将来 `building_effects` に行を追加して機能を増やせるようにする。

## 5. データモデル

型はPostgreSQLに準拠(Supabaseを利用するため)。
名前と細部は migration 作成時に確定する。

#### 凡例

- PK: Primary Key
- FK: Foreign Key
- UNIQUE: 一意制約
- nullable: NULL 許容
- `timestamptz`: タイムゾーン付きタイムスタンプ

### 5.1 `profiles`

| 列             | 型            | 説明            |
| -------------- | ------------- | --------------- |
| `id`           | `uuid` PK/FK  | `auth.users.id` |
| `display_name` | `text`        | 公開表示名      |
| `created_at`   | `timestamptz` | 作成日時        |
| `updated_at`   | `timestamptz` | 更新日時        |

- Supabase Auth でユーザーが作成されると、EF で `profiles` に行を作成する。
- `display_name` はユーザーが変更可能。公開プロフィールとして他ユーザーに表示される。

### 5.2 `towns`

| 列           | 型               | 説明                 |
| ------------ | ---------------- | -------------------- |
| `id`         | `uuid` PK        | 街 ID                |
| `owner_id`   | `uuid` UNIQUE/FK | 所有者               |
| `name`       | `text`           | 街名                 |
| `coins`      | `bigint`         | 所持コイン。0 以上   |
| `population` | `bigint`         | 集計済み人口。0 以上 |
| `map_width`  | `smallint`       | 最大 100             |
| `map_height` | `smallint`       | 最大 100             |
| `created_at` | `timestamptz`    | 作成日時             |
| `updated_at` | `timestamptz`    | 更新日時             |

初期値は `map_width = 100`、`map_height = 100` とし、初期開放状態は別テーブルで 20×20 を表現する。

- `coins` は即時表示用の残高、`coin_ledger` は根拠と監査用の台帳とする。
- 両方を同じトランザクションで更新する。

### 5.3 `building_types`

| 列                | 型                | 説明                               |
| ----------------- | ----------------- | ---------------------------------- |
| `code`            | `text` PK         | 安定した識別子                     |
| `name`            | `text`            | 表示名                             |
| `category`        | `text`            | 建物分類。将来の効果対象指定に使用 |
| `width`           | `smallint`        | 1 または 2                         |
| `height`          | `smallint`        | 1 または 2                         |
| `cost_coins`      | `bigint` nullable | 未決定中は `null`、販売時は 0 以上 |
| `description`     | `text`            | 表示用説明                         |
| `enabled`         | `boolean`         | 購入可能か                         |
| `catalog_version` | `integer`         | 契約・キャッシュ更新用             |

価格未決定の項目は `enabled = false` とし、`null` を無料の意味に使わない。

### 5.4 `building_effects`

| 列                   | 型                 | 説明                   |
| -------------------- | ------------------ | ---------------------- |
| `id`                 | `uuid` PK          | 効果 ID                |
| `building_type_code` | `text` FK          | 建物種別               |
| `effect_type`        | `text`             | 効果の種類             |
| `value`              | `numeric` nullable | 効果量。未決定可       |
| `target_category`    | `text` nullable    | 対象カテゴリ           |
| `scope`              | `text` nullable    | 街全体・周辺等。TBD 可 |
| `stacking_rule`      | `text` nullable    | 加算・上限等。TBD 可   |
| `metadata`           | `jsonb`            | 将来の追加パラメータ   |

初期効果タイプの候補:

- `population_flat`: 固定人口加算
- `step_coin_bonus_flat`: 歩数同期時のコイン固定増加
- `residential_population_bonus`: 住宅（小）への人口加算
- `enables_adjacent_construction`: 周辺建築の許可

効果タイプを追加するときは、未知の値を暗黙に実行せず、対応する評価ロジックとテストを追加する。

### 5.5 `placed_buildings`

| 列                     | 型            | 説明                  |
| ---------------------- | ------------- | --------------------- |
| `id`                   | `uuid` PK     | 配置物 ID             |
| `town_id`              | `uuid` FK     | 所属する街            |
| `building_type_code`   | `text` FK     | 建物種別              |
| `anchor_x`             | `smallint`    | 左上アンカーの X 座標 |
| `anchor_y`             | `smallint`    | 左上アンカーの Y 座標 |
| `purchased_cost_coins` | `bigint`      | 購入時価格の記録      |
| `created_at`           | `timestamptz` | 配置日時              |
| `updated_at`           | `timestamptz` | 移動日時              |

回転列は設けない。複数セル占有は矩形同士の重なり判定、または占有セル用テーブルで保証する。DB 関数内で対象の街をロックして検証する。

### 5.6 `unlocked_cells` または `unlocked_areas`

初期 20×20 と追加開放領域を表現する。セル単位か矩形単位かは、土地開放ルール決定後に選ぶ。

- 10x10で拡張とか、 1x1で拡張とか、将来の仕様変更に備えて柔軟に対応できるようにする。 (とりあえず後で考える)

| 列              | 型            | 説明                              |
| --------------- | ------------- | --------------------------------- |
| `town_id`       | `uuid` FK     | 街 ID                             |
| `x`, `y`        | `smallint`    | セル方式の場合の座標              |
| `unlocked_at`   | `timestamptz` | 開放日時                          |
| `unlock_method` | `text`        | `coins`、`item`、`total_steps` 等 |

### 5.7 `daily_step_records`

| 列               | 型            | 説明                             |
| ---------------- | ------------- | -------------------------------- |
| `id`             | `uuid` PK     | 記録 ID                          |
| `user_id`        | `uuid` FK     | ユーザー                         |
| `step_date`      | `date`        | 集計対象日                       |
| `steps`          | `integer`     | Google Health から確認できた歩数 |
| `rewarded_steps` | `integer`     | コイン精算済み歩数               |
| `source`         | `text`        | 外部データソース識別子           |
| `synced_at`      | `timestamptz` | 最終同期日時                     |

- `unique(user_id, step_date, source)` を設定する。日付境界のタイムゾーンはプロダクト方針として決定し、全処理で統一する（現時点 TBD）。
- `rewarded_steps` は、すでにコイン付与済みの歩数を記録する。再同期時に差分だけを計算する。

### 5.8 `coin_ledger`

| 列                | 型            | 説明                                  |
| ----------------- | ------------- | ------------------------------------- |
| `id`              | `uuid` PK     | 台帳 ID                               |
| `town_id`         | `uuid` FK     | 対象の街                              |

| `metadata`        | `jsonb`       | 対象日、歩数差分、建物 ID 等          |
| `created_at`      | `timestamptz` | 記録日時                              |

`towns.coins` は即時表示用の残高、`coin_ledger` は根拠と監査用の台帳とする。両方を同じトランザクションで更新する。

Google 側の認可情報が必要な場合に使用する。ユーザーから読み取れる通常テーブルへアクセストークンや更新トークンを保存しない。Supabase Secrets、暗号化、トークン更新方式を含め、採用 API の公式要件に合わせて実装する。

## 7. ゲームロジック

### 7.1 歩数同期とコイン付与

EF `health_steps_fetch` の処理:

1. Supabase JWT からユーザーを特定する。 (authとRLSで本人確認)
2. Google Health 連携状態と必要権限を確認する。 (認可されていないとそもそも使えないため、エラーを返す)
3. Google Health API から対象期間の歩数を取得する。 (stepsエンドポイントを利用)
4. 日別レコードを upsert する。
5. すでに報酬計算済みの歩数との差分を求める。(rewarded_steps と比較)
6. 基本変換率と配置済み建物のコイン増加効果をサーバー設定から読む。(TBD)
7. 新たに付与するコインを計算する。(式: `new_coins = floor(diff_steps * base_rate) + sum(building_effects)`。端数処理、日次上限、商業施設・工場の「1つにつき +50」が固定値か倍率か、複数設置時の上限はすべて TBD)
8. 一意なキーで `coin_ledger` に記録し、残高を更新する。
9. 更新後の歩数、獲得コイン、残高、同期日時を返す。

基本変換式、端数処理、日次上限、商業施設・工場の「1つにつき +50」が固定値か倍率か、複数設置時の上限はすべて TBD。これらはバージョン付き設定として管理する。

増加率は別に固定値のほうが実装しやすいような気もする。要検討。

同じ歩数を再同期しても追加コインを付与しない。後から歩数が増えた場合は、未精算差分だけを対象にする。

### 7.2 建物購入と配置

DB 関数 `place_building` の処理:

1. 認証ユーザーが街の所有者であることを確認する。 (auth + RLS)
2. カタログ項目が有効で価格確定済みか確認する。 (enabled = true、cost_coins != null)
3. アンカーと全占有セルが 100×100 内にあることを確認する。 (`anchor_x >= 0 && anchor_y >= 0 && anchor_x + width <= map_width && anchor_y + height <= map_height`)
4. 全占有セルが開放済みか確認する。 (`unlocked_cells` または `unlocked_areas` を参照)
5. 全占有セルが既存建物・道路・将来の障害物と重ならないことを確認する。 (`placed_buildings` と `map_obstacles` を参照)
6. 道路以外の建物について、確定した道路隣接条件を確認する。
7. 残高をロックし、コインが足りるか確認する。
8. コイン台帳、残高、配置物を一つのトランザクションで更新する。
   1. `coin_ledger` に記録する。
   2. `towns.coins` を減算する。
   3. `placed_buildings` に新しい建物を追加する。
   4. `towns.population` を更新する。
   5. `towns.updated_at` を更新する。
   6. `placed_buildings.updated_at` を更新する。
   7. `coin_ledger.created_at` を更新する。
   8. `towns.updated_at` を更新する。
   9. `placed_buildings.created_at` を更新する。
9. 人口を再計算する。
10. 更新後の街スナップショットを返す。

道路自体の配置条件、および最初の道路をどこに置けるかは TBD。

### 7.3 建物移動

DB 関数 `move_building` は所有権、境界、開放状態、衝突、道路条件を再検証する。移動ではコインを消費しない。将来「周辺」を効果範囲に使う場合は移動後に人口・効果を再計算する。

### 7.4 人口計算

人口は配置済み建物と効果設定からサーバー側で計算する。

- 住宅（小）1軒につき +10 人
- 農場 1つにつき +5 人
- 役所は、効果対象となる住宅（小）1軒につきさらに +20 人
- その他の建物の人口効果は現時点でなし

役所効果の適用範囲、複数役所の重複方法が決まるまでは役所効果を無効とする。決定後は計算関数を一か所に実装し、`towns.population` を同じトランザクションで更新する。

### 7.5 土地開放

初期開放は 20×20。原点から開放するか、100×100 の中央から開放するかは TBD。

将来の開放方式としてコイン消費、アイテム消費、合計歩数の達成を許容する。実際に採用する方式、開放単位、価格、順序は未確定。API は開放方法と必要条件を設定データから返せる構造にする。

### 7.6 ランキング

`towns.population` の降順で全ユーザーを順位付けする。同率順位の扱い、ページサイズ、非公開設定の有無は TBD。安定したページングのため、同率時の第2ソートキーを決定する。

## 8. 認証・認可

### Google ログイン

Supabase Auth の Google Provider を使用する。OAuth リダイレクト URL は開発・本番環境ごとに許可リストへ登録する。

Google ログインのスコープと Google Health データ取得のスコープは同一とは限らない。
GoogleのAIモードによると、『SupabaseでGoogle認証（Google Login）を行うためにGoogle Cloud Console側で有効にする必要がある特定の独立したAPIサービスは特にありません』とのこと。

(分ける場合はAPIを別途もう一回発行する必要があるかも。~~面倒なので~~別に分けなくてもいいか？)<br>
必要に応じて連携同意を分け、最小権限だけを要求する。

### RLS 方針

| データ                 |     本人 |     他ユーザー | Service Role / EF |
| ---------------------- | -------: | -------------: | ----------------: |
| 自分のプロフィール更新 |       可 |           不可 |        必要時のみ |
| 公開プロフィール読取   |       可 |             可 |                可 |
| 歩数・連携情報         |       可 |           不可 |                可 |
| 自分の街・配置物読取   |       可 | 公開項目のみ可 |                可 |
| 街・配置物の直接書込   |     不可 |           不可 |      RPC 経由のみ |
| カタログ読取           |       可 |             可 |                可 |
| カタログ書込           |     不可 |           不可 |      管理処理のみ |
| コイン台帳             | 本人のみ |           不可 |                可 |

クライアントからテーブルへ直接 `insert/update` して残高や配置を変更させず、権限を限定した DB 関数または EF を経由する。

## 9. EF と DB Function の分担

- EF: Google API 呼び出し、OAuth/トークン処理、外部レスポンスの正規化。
- DB Function/RPC: コイン台帳、購入、配置、移動、人口再計算など、DB 内で完結するトランザクション。
- 通常クエリ: カタログ、自分の街、公開街、ランキングの読み取り。

- 外部 API の呼び出し中に DB ロックを保持しない。
  Google Health API の呼び出しは数百ミリ秒～数秒かかる可能性がある。<br>
  DBのトランザクションを長時間保持すると他のユーザーの操作をブロックしてしまう。(最悪デッドロックも...？)<br>
  そのため、歩数を取るEFを先に呼び出してから更新する。

取得した歩数を正規化してから、短い DB トランザクションへ渡す。

```postgresql
--- 歩数の同期。カラム名は仮のもの
upsert into daily_step_records (user_id, step_date, steps, rewarded_steps, source, synced_at)
values (user_id, step_date, steps, rewarded_steps, source, synced_at)
on conflict (user_id, step_date, source) do update set steps = excluded.steps, rewarded_steps = excluded.rewarded_steps, synced_at = excluded.synced_at;
```

## 10. エラーコード

| エラーコード                 | 説明                             |
| ---------------------------- | -------------------------------- |
| `UNAUTHENTICATED`            | 未認証                           |
| `HEALTH_NOT_CONNECTED`       | Google Health が未接続           |
| `HEALTH_PERMISSION_REQUIRED` | Google Health の権限が必要       |
| `HEALTH_PROVIDER_ERROR`      | ヘルスデータ提供元でエラーが発生 |
| `INVALID_INPUT`              | 入力値が不正                     |

## 11. テスト観点

### 歩数・コイン

- 同じデータを複数回同期しても二重付与されない。
- 増加分だけが次回付与される。
- 商業施設・工場の個数と設定に応じた値になる。
- 外部 API 失敗時に歩数や残高が中途半端に更新されない。
- 別ユーザーの歩数・連携情報を読めない。

### 建築

- 1×1、2×2 の境界と重なりを正しく判定する。
- `(99, 99)` に 2×2 を置けない。
- 未開放セルを一部でも含む建物を置けない。
- 道路条件を満たさない建物を置けない。
- 同時購入でも残高が負にならない。
- 購入失敗時に建物だけ作成されない。
- 他ユーザーの建物を移動できない。

### 人口・公開機能

- 農場ごとに +5 人になる。
- 住宅（小）ごとに +10 人になる。
- 役所の範囲・重複仕様確定後、住宅（小）への +20 人を単体・複数設置でテストする。
- ランキングの値と街の人口が一致する。
- 公開 API から残高、歩数、連携情報が漏れない。
