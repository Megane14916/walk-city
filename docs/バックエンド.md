# Walk City バックエンド設計書

## 1. この文書の目的

Walk City の Supabase
バックエンドが管理するデータ、認証、歩数同期、ゲームロジック、権限制御を定義する。

コイン残高、建物配置、人口、土地開放、ランキングはバックエンドを唯一の正とする。
価格や効果値は設定データで管理し、ゲームバランス変更のたびにフロントエンドや関数を改修しない構造にする。
バックエンドのフレームワークは不要？RPCとSupabase Edge Functions
(以下、「EF」)だけで十分？

とりあえず一人で追記修正していく方針。

利用するAIエージェント

- GitHub Copilot (コード補完 / VS Code)
- Google Gemini (学割特権の「Pro」モデルで)
- (できれば) Claude Code (Proプラン必須。コード検証等)

## 2. 技術構成

- Supabase Auth（Google ログイン。以下「Auth」と表記）
- Supabase PostgreSQL (以下「DB」)
- Row Level Security（RLS） (データ更新や表示の制限を行う)
- Supabase EF (Edge Functions。Google Health APIの連携 / 新しいユーザー登録)
- Google Health API（正式な API 名、認可方式、Web
  アプリから取得可能な歩数データは実装前に確認する）

Google Health 連携は EF 内のアダプターへ隔離する。利用する Google 側 API
が変更されても、ゲームロジックとフロントエンドの契約へ影響を広げない。

歩数の取得はGoogle Health APIのstepsの項目からとる。

## 3. セキュリティのための設計プラン

- Googleのログイン、およびGoogle Health
  APIに利用する認可コード、アクセストークンは、Edge Function内でだけ扱い、DBテーブルやレスポンスへ保存・返却しない。ユーザーごとに異なるリフレッシュトークンは静的なSecretsへ保存できないため、暗号化キーだけをSupabaseのEFのSecretsに保存し、暗号化済みのトークン自体はData
  API・RLS経由でクライアントから到達できない`private`スキーマのテーブル（`private.health_tokens`）へユーザーごとに保存する。`anon`
  / `authenticated` ロールの権限は剥奪し、読み書きはEdge Functionが呼び出すSECURITY DEFINER関数だけに限定する。
- SupabaseのRLSで、ユーザーが自分のプロフィール、街、歩数、コイン台帳を操作できるようにする。ユーザーは他人のデータを直接操作できない(公開するものは読み出しのみ可能)。
- EFは、Google Health
  APIの呼び出し、認可コードの交換、アクセストークンの更新を行う。DB関数は、コイン台帳、建物配置、人口計算などのトランザクションを行う。
- フロントでは外部APIの利用を行わず、必ずEF(以下、EF)を経由し、fetchが完了したらRPCを呼び出す。
- EFはGoogle Health
  APIの呼び出し中にDBロックを保持しない。(最悪デッドロックもあり)
- DB関数は、コイン台帳、建物配置、人口計算などのトランザクションを行う。

## 3. バックエンドの責務

- Google ログイン済みユーザーの識別
- プロフィールと街の初期作成
- Google Health の認可情報の安全な取り扱い
- 歩数の取得・日別保存・重複同期の防止
- 歩数からコインへの変換と付与
- 建物カタログ、価格、サイズ、効果の管理
- 建物・道路の購入、配置、移動
- マップ境界、土地開放、衝突、道路条件の検証
- 人口の計算
- 全ユーザー人口ランキング
- 他ユーザーに公開する街データの提供
- RLS、入力検証、トランザクション、監査可能な台帳

## 4. 設計原則

### 4.1 サーバー権威

クライアントが送るコイン、人口、価格、建物サイズ、効果値、ユーザー ID
を信用しない。 認証ユーザーとサーバー上のカタログ・街データから計算する。

### 4.2 原子的な更新

次の操作はそれぞれ一つのトランザクションで完了させる。

- 歩数の差分記録とコイン付与
- コイン減算と建物配置
- 建物移動と配置検証
- 土地開放条件の検証と開放状態更新

途中だけ成功する状態を作らない。

### 4.3 データ駆動の建物効果

建物の共通項目と効果を分離する。効果がない建物も空配列として扱い、将来
`building_effects` に行を追加して機能を増やせるようにする。

## 5. データモデル

型はPostgreSQLに準拠(Supabaseを利用するため)。 名前と細部は migration
作成時に確定する。

#### 凡例

- PK: Primary Key
- FK: Foreign Key
- UNIQUE: 一意制約
- nullable: NULL 許容 (無記載はNOT NULL)

##### デフォルト値

- n/a : Foreign Keyなどのため、デフォルト値が不要なこと。

以下データモデルはすべて作成済み。
</span>

### 5.1 `profiles`

| 列             | 型            | 説明            | デフォルト値           |
| -------------- | ------------- | --------------- | ---------------------- |
| `id`           | `uuid` PK/FK  | `auth.users.id` | n/a                    |
| `display_name` | `text`        | 公開表示名      | `user-xxxxxxxx`（UUID由来） |
| `created_at`   | `timestamptz` | 作成日時        | now()                  |
| `updated_at`   | `timestamptz` | 更新日時        | now()                  |

- Google OAuthコールバックでセッション復元後に`initialize-user` EFを呼び、`profiles`を含む初期データを作成する。新規登録と再ログインの両方で冪等に呼び、導入前から存在するAuthユーザーは次回ログイン時に不足データだけを遅延作成する。全件backfill migrationは行わない。
- `display_name`は公開プロフィールとして他ユーザーに表示される。初期値は認証ユーザーUUIDからハイフンを除いた先頭8文字を使う`user-xxxxxxxx`とし、同じユーザーでは常に同じ値を生成する。
- DB列は将来変更できる設計を維持するが、MVPではプロフィール表示名の変更APIとUIを実装しない。

公開スキーマの接続状態テーブル。`status`、`scopes`、`connected_at`、`last_synced_at`などの状態列だけを持ち、本人はRLS経由で読み取れる。アクセストークンや更新トークンなど機密値はこのテーブルへ保存しない。

### 5.13 `private.health_tokens`

更新トークン本体を暗号化して保持する非公開スキーマのテーブル。`user_id`、暗号化済み`refresh_token`、`updated_at`程度の列を持つ。`anon`
/ `authenticated`
からの直接アクセス権を剥奪し、読み書きはEdge Functionが呼び出すSECURITY DEFINER関数だけに限定する。暗号鍵はSupabase
EF Secretsに保存し、テーブル本体には含めない。Supabase Secrets、暗号化、トークン更新方式を含め、採用 API
の公式要件に合わせて実装する。

## 7. ゲームロジック

### 7.1 歩数同期とコイン付与

EF `sync-health-steps` の処理:

1. Supabase JWT からユーザーを特定する。 (authとRLSで本人確認)
  `profiles.id = auth.uid()` で本人確認する。
2. Google Health 連携状態と必要権限を確認する。
   (認可されていないとそもそも使えないため、省略して先にエラーを飛ばす)
3. EF内の非公開モジュールからGoogle Health v4 `dailyRollUp`を呼び、`Asia/Tokyo`の当日歩数を取得する。
4. 日別レコードを upsert する。
5. すでに報酬計算済みの歩数との差分を求める。(rewarded_steps と比較)
6. 10歩につき1コイン、端数切り捨て、日次上限なしで基本報酬を計算する。
7. 同日の追加同期では`base_coins = max(0, floor(total_steps / 10) - floor(previous_rewarded_steps / 10))`とし、分割同期で端数を失わない。商業施設と工場の合算ボーナス率（最大50%）を掛け、適用後の小数点以下を切り捨てる。
8. 一意なキーで `coin_ledger` に記録し、残高を更新する。
9. 更新後の歩数、獲得コイン、残高、同期日時を返す。

`google_health_fetch`、`health_steps_fetch`、表示専用`get-daily-steps`は公開・deploy対象から外し、歩数取得と精算を`sync-health-steps`へ統合する。OAuth開始、callback、接続状態取得、切断用EFは別責務として維持する。

同じ歩数を再同期しても追加コインを付与しない。後から歩数が増えた場合は、未精算差分だけを対象にする。

### 7.2 建物購入と配置

Supabase SQL Editorで実行するRPCの例。`unlocked_cells` は `(town_id, x, y)`、
`placed_buildings` は `(town_id, anchor_x, anchor_y, width, height)` を持つ前提とする。
道路隣接条件は上下左右の4方向、斜めは含めないことで確定した。以下のSQL例は確定前の簡略版であり、道路隣接検証は含めていない。

以下、place_buildingのSQL関数。
```sql
create or replace function public.place_building(
  p_town_id uuid, -- townsのtown_id
  p_building_type_code text, -- building_typesのcode(何を建てるか)
  p_anchor_x integer, -- X座標
  p_anchor_y integer, -- Y座標
  p_idempotency_key uuid -- coin_ledgerのidempotency_key(二重反映防止)
)
returns public.towns
language plpgsql
security invoker
set search_path = public
as $$
declare
  v_town public.towns%rowtype; -- 返却用
  v_type record; -- building_typesの行
  v_existing record; -- coin_ledgerの既存行
  v_width integer; -- building_types.width
  v_height integer; -- building_types.height
  v_cost bigint; -- building_types.cost_coins
  v_building_id uuid; -- placed_buildings.id
  v_population integer; -- 計算後の人口
begin
  select * into v_town
    from public.towns
   where id = p_town_id and owner_id = auth.uid()
   for update;
  if not found then
    raise exception 'town_not_found_or_forbidden' using errcode = '42501';
  end if;

  select bt.width, bt.height, bt.cost_coins, bt.enabled, bt.is_road
    into v_type
    from public.building_types bt
   where bt.code = p_building_type_code;
  if not found or not v_type.enabled or v_type.cost_coins is null then
    raise exception 'building_type_unavailable' using errcode = '22023';
  end if;
  v_width := v_type.width;
  v_height := v_type.height;
  v_cost := v_type.cost_coins;

  select * into v_existing
    from public.coin_ledger
   where town_id = p_town_id and idempotency_key = p_idempotency_key;
  if found then
    select * into v_town from public.towns where id = p_town_id;
    return v_town;
  end if;

  if p_anchor_x < 0 or p_anchor_y < 0
     or p_anchor_x + v_width > 100 or p_anchor_y + v_height > 100 then
    raise exception 'building_out_of_bounds' using errcode = '22023';
  end if;

  for x in p_anchor_x..p_anchor_x + v_width - 1 loop
    for y in p_anchor_y..p_anchor_y + v_height - 1 loop
      if not exists (select 1 from public.unlocked_cells
                      where town_id = p_town_id and x = x and y = y) then
        raise exception 'cell_locked' using errcode = '22023';
      end if;
      if exists (select 1 from public.placed_buildings b
                  where b.town_id = p_town_id
                    and b.anchor_x < x + 1 and b.anchor_x + b.width > x
                    and b.anchor_y < y + 1 and b.anchor_y + b.height > y)
         or exists (select 1 from public.map_obstacles o
                     where o.town_id = p_town_id and o.x = x and o.y = y) then
        raise exception 'cell_occupied' using errcode = '22023';
      end if;
    end loop;
  end loop;

  if v_town.coins < v_cost then
    raise exception 'insufficient_coins' using errcode = 'P0001';
  end if;

  update public.towns
     set coins = coins - v_cost, updated_at = now()
   where id = p_town_id;
  insert into public.coin_ledger
    (town_id, amount, reason, idempotency_key, created_at)
  values (p_town_id, -v_cost, 'building_purchase', p_idempotency_key, now());
  insert into public.placed_buildings
    (town_id, building_type_code, anchor_x, anchor_y, width, height,
     created_at, updated_at)
  values (p_town_id, p_building_type_code, p_anchor_x, p_anchor_y, v_width,
          v_height, now(), now())
  returning id into v_building_id;

  select coalesce(sum(case when building_type_code = 'small_house' then 10
                           when building_type_code = 'apartment' then 50 else 0 end), 0)
    into v_population
    from public.placed_buildings where town_id = p_town_id;
  update public.towns set population = v_population where id = p_town_id;
  select * into v_town from public.towns where id = p_town_id;
  return v_town;
end;
$$;

revoke all on function public.place_building(uuid, text, integer, integer, uuid)
  from public;
grant execute on function public.place_building(uuid, text, integer, integer, uuid)
  to authenticated;
```

本番適用前に、実際のカラム名・型に合わせて調整し、`coin_ledger(town_id,
idempotency_key)` に一意制約を追加する。`unlocked_cells`、`placed_buildings`、
`map_obstacles` にはRLSも設定し、RPCの引数はクライアントから直接信頼しない。
DB 関数 `place_building` の処理:

1. 認証ユーザーが街の所有者であることを確認する。 (auth + RLS)
2. カタログ項目が有効で価格確定済みか確認する。 (enabled = true、cost_coins != null)
3. アンカーと全占有セルが 100×100 内にあることを確認する。 (`anchor_x >= 0 && anchor_y >= 0 && anchor_x + width <= map_width && anchor_y + height <= map_height`)
4. 全占有セルが開放済みか確認する。 (`unlocked_cells` または `unlocked_areas` を参照)
5. 全占有セルが既存建物・道路・将来の障害物と重ならないことを確認する。 (`placed_buildings` と `map_obstacles` を参照)
6. 全占有セルが固定地形の配置ルールを満たすことを確認する。通常建物が川に重なる場合は `RIVER_BLOCKED` とする。
7. 道路以外の建物について、確定した道路隣接条件を確認する。
8. 残高をロックし、コインが足りるか確認する。
9. コイン台帳、残高、配置物を一つのトランザクションで更新する。
   1. `coin_ledger` に記録する。
   2. `towns.coins` を減算する。
   3. `placed_buildings` に新しい建物を追加する。
   4. `towns.population` を更新する。
   5. `towns.updated_at` を更新する。
   6. `placed_buildings.updated_at` を更新する。
   7. `coin_ledger.created_at` を更新する。
   8. `towns.updated_at` を更新する。
   9. `placed_buildings.created_at` を更新する。
10. 人口を再計算する。
11. 更新後の街スナップショットを返す。

道路は DB 関数 `place_road_line` で連続した直線セルを一括配置する。川に触れない場合は通常道路として処理し、既存の通常道路と重なるセルを新規配置・課金から除外する。川に触れる場合は、川と直交する連続 7 セル（陸 1 + 川 5 + 陸 1）、全セル開放済み・未占有、直線領域のみ、という条件をすべて満たした場合だけ橋へ自動変換する。周囲に既存道路がなくてもよく、隣接する橋の数に制限を設けない。

橋の価格は川上 5 セルを各 200 コイン、両岸 2 セルを各通常道路価格として計算する。`road_structures` 1 行、`placed_buildings` 7 行、コイン台帳、残高を同じトランザクションで更新する。クライアントから橋判定・価格・構造 ID を受け取らない。

### 7.3 建物移動

DB 関数 `move_building` は所有権、境界、開放状態、衝突、固定地形、道路条件を再検証する。移動ではコインを消費しない。道路カテゴリまたは橋グループに属する配置物は `PLACEMENT_IMMOVABLE` として拒否する。将来「周辺」を効果範囲に使う場合は移動後に人口・効果を再計算する。

### 7.4 道路・橋の削除

DB 関数 `delete_road` は `building_id` と `request_id` を受け取る。

1. 認証ユーザーが所有者であり、対象が道路であることを確認する。
2. 対象、街、必要なら橋グループをロックする。
3. 通常道路なら指定した 1 セルだけ、橋なら同じ `road_structure_id` の 7 セルすべてを削除する。
4. 削除後も道路隣接を必要とする既存建物が条件を満たすことを検証する。壊れる場合は `ROAD_IN_USE` として全処理を戻す。
5. 橋グループが 7 セルでなければ `BRIDGE_GROUP_INVALID` として部分削除しない。
6. 返金とコイン台帳追加は行わず、街の更新日時だけを更新する。

同じ `request_id` の再送は初回と同じ結果を返し、橋の 7 セルと `road_structures` の削除は一つのトランザクションで行う。

### 7.5 人口計算

人口は配置済み建物と効果設定からサーバー側で計算する。固定加算の後に公園・役所の加算を行い、最後に病院10%を切り捨てて加える。詳細は [建物効果仕様.md](./建物効果仕様.md) に従う。

人口計算関数は一か所に実装し、`towns.population` を同じトランザクションで更新する。

### 7.6 土地開放

初期開放は 100×100 マップ中央の 20×20 とする。左上は `(40, 40)`、右下は `(59, 59)` とする。

MVPでは20×20単位、1000コイン、左上アンカーは20の倍数とする。既存開放領域と上下左右の辺で隣接する区画だけを許可し、斜め隣接は拒否する。残高減算、コイン台帳、開放領域追加は`unlock_land` RPCの一つのトランザクションで行い、`requestId`で二重消費を防ぐ。

### 7.7 ランキング

`towns.population`
の降順で全ユーザーを順位付けする。同率順位の扱い、ページサイズ、非公開設定の有無は
TBD。安定したページングのため、同率時の第2ソートキーを決定する。

## 8. 認証・認可

### Google ログイン

Supabase Auth の Google Provider を使用する。OAuth リダイレクト URL
は開発・本番環境ごとに許可リストへ登録する。

GoogleのAIモードによると、
『SupabaseでGoogle認証（Google Login）を行うためにGoogle Cloud Console側で有効にする必要がある特定の独立したAPIサービスは特にありません』とのこと。
必須要件はGAuthのprofile、email、openidの3つのスコープだけで十分。Health APIは別途有効化する形。

### RLS 方針

| データ                 |     本人 |     他ユーザー | Service Role / EF |
| ---------------------- | -------: | -------------: | ----------------: |
| 自分のプロフィール更新 |       可 |           不可 |        必要時のみ |
| 公開プロフィール読取   |       可 |             可 |                可 |
| 歩数・連携情報         |       可 |           不可 |                可 |
| 自分の街・配置物読取   |       可 | 公開項目のみ可 |                可 |
| 街・配置物の直接書込   |     不可 |           不可 |      RPC 経由のみ |
| カタログ読取           |       可 |             可 |                可 |
| カタログ書込           |     不可 |           不可 |      管理処理のみ |
| 固定マップ・地形読取   |       可 |             可 |                可 |
| 固定マップ・地形書込   |     不可 |           不可 |      管理処理のみ |
| 道路構造読取           |       可 | 公開項目のみ可 |                可 |
| 道路構造の直接書込     |     不可 |           不可 |      RPC 経由のみ |
| コイン台帳             | 本人のみ |           不可 |                可 |

クライアントからテーブルへ直接 `insert/update`
して残高や配置を変更させず、権限を限定した DB 関数または EF を経由する。

## 9. EF と DB Function の分担

- EF: Google API 呼び出し、OAuth/トークン処理、外部レスポンスの正規化。
- DB Function/RPC: コイン台帳、購入、配置、移動、道路・橋の削除、人口再計算など、DB 内で完結するトランザクション。
- 通常クエリ: カタログ、自分の街、公開街、ランキングの読み取り。

- 外部 API の呼び出し中に DB ロックを保持しない。
- Google Health APIの呼び出しは数百ミリ秒～数秒かかる可能性がある。<br>
  DBのトランザクションを長時間保持すると他のユーザーの操作をブロックしてしまう。(最悪デッドロックも...？)<br>
  そのため、歩数を取るEFを先に呼び出してから更新する。

取得した歩数を正規化してから、短い DB トランザクションへ渡す。

```postgresql
--- 歩数の同期。カラム名は仮のもの
upsert into daily_step_records (user_id, step_date, steps, rewarded_steps, source, synced_at)
values (user_id, step_date, steps, rewarded_steps, source, synced_at)
on conflict (user_id, step_date, source) do update set steps = excluded.steps, rewarded_steps = excluded.rewarded_steps, synced_at = excluded.synced_at;
```

## 11. テスト観点

### 歩数・コイン

- 同じデータを複数回同期しても二重付与されない。
- 増加分だけが次回付与される。
- 商業施設の個数と設定に応じた値になる。
- 外部 API 失敗時に歩数や残高が中途半端に更新されない。
- 別ユーザーの歩数・連携情報を読めない。

### 建築

- 1×1、2×2 の境界と重なりを正しく判定する。
- `(99, 99)` に 2×2 を置けない。
- 未開放セルを一部でも含む建物を置けない。
- 道路条件を満たさない建物を置けない。
- 同時購入でも残高が負にならない。
- 購入失敗時に建物だけ作成されない。
- 他ユーザーの建物を移動できない。
- 通常建物を川セルへ配置できない。
- 川の直線部分を直交する 7 セルだけが橋として保存される。
- 曲がり角、平行方向、6 セル以下、8 セル以上、未開放セルを含む橋候補を拒否する。
- 橋価格が川上 5 セル各 200 コインと両岸の通常道路価格の合計になる。
- 道路と橋を移動できない。
- 通常道路は指定した 1 セルだけ削除される。
- 橋は 7 セルと構造行が一括削除され、失敗時に部分削除されない。
- 道路削除により既存建物の道路条件が壊れる場合は拒否する。

### 人口・公開機能

- 農場ごとに人口が +20 になる。
- 住宅（小）ごとに +10 人になる。
- 住宅（大）ごとに +50 人になる。
- 役所は1軒分だけ、住宅（小）ごとに人口 +20 を適用する。
- 公園の隣接判定、病院10%の切り捨て、各効果の重複上限が正しい。
- ランキングの値と街の人口が一致する。
- 公開 API から残高、歩数、連携情報が漏れない。
