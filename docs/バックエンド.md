# 散歩×街づくりゲーム バックエンド開発計画書

## 1. 目的

歩数報酬、所持コイン、街の建物配置、人口、ランキング、いいねを安全かつ一貫して管理し、フロントエンドへ安定したインターフェースを提供する。

開発期間は1週間。フロントエンドとは `shared-api-contract.md` に従って並行開発する。

## 2. 推奨技術構成

```text
Supabase Auth
Supabase PostgreSQL
Row Level Security
Database Functions / RPC
```

理由:

- ユーザー、街、建物、いいね、ランキングをリレーショナルに扱える
- ReactからSDKで接続できる
- 認証とDBを同じサービスで管理できる
- 所有者だけが編集できる権限をRLSで表現できる

チームにFirebase経験者がいる場合は置き換えてよい。ただしAPI契約と検証ルールは維持する。

## 3. バックエンドの担当範囲

- 認証とユーザー識別
- プロフィールと街の初期作成
- 日次歩数の保存
- 段階報酬の判定と二重取得防止
- コイン、建築チケットの残高管理
- 建物カタログの提供
- 建物購入、配置、移動
- 土地開放、固定障害物、衝突の検証
- 人口の計算
- 週間散歩回数の計算
- 街訪問用データ
- いいねの一意性と自己いいね防止
- 総人口、週間人口増加ランキング
- API/RPCのエラー形式
- デモ用シードデータ

## 4. データモデル

### profiles

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK/FK | 認証ユーザーID |
| display_name | text | ユーザー名 |
| coins | integer | 所持コイン |
| building_tickets | integer | 建築チケット |
| created_at | timestamptz | 作成日時 |

制約:

- `coins >= 0`
- `building_tickets >= 0`

### towns

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | 街ID |
| user_id | uuid UNIQUE | 所有者 |
| name | text | 街名 |
| population | integer | ランキング用キャッシュ |
| unlock_level | integer | 土地開放段階 |
| terrain_version | integer | 固定地形の版 |
| created_at | timestamptz | 作成日時 |

### walk_records

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | 記録ID |
| user_id | uuid | ユーザー |
| walk_date | date | 日本時間の日付 |
| steps | integer | 当日の最大登録歩数 |
| qualified | boolean | 3,000歩以上か |
| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 更新日時 |

制約:

- `unique(user_id, walk_date)`
- `0 <= steps <= 100000`

### reward_claims

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | 取得ID |

| walk_date | date | 対象日 |
| tier_steps | integer | 1000/3000/5000/8000 |
| coins_awarded | integer | 取得時の報酬 |
| tickets_awarded | integer | 取得時の報酬 |
| created_at | timestamptz | 取得日時 |

制約:

- `unique(user_id, walk_date, tier_steps)`

### building_catalog

| 列 | 型 | 説明 |
|---|---|---|
| type | text PK | 建物種別 |
| name | text | 表示名 |
| cost_coins | integer | 価格 |
| cost_tickets | integer | チケット価格 |
| population_value | integer | 人口効果 |
| required_population | integer | 解放条件 |
| sprite_key | text | フロント画像キー |

### placed_buildings

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | 建物ID |

| y | integer | Y座標 |

| created_at | timestamptz | 建築日時 |

制約:

- `unique(town_id, x, y)`
- 座標は0〜19

### town_likes

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | いいねID |
| from_user_id | uuid | 送信者 |
| town_id | uuid | 対象街 |
| created_at | timestamptz | 送信日時 |

制約:

- `unique(from_user_id, town_id)`
- 自分の街への挿入は禁止

## 5. 認証と権限

### 読み取り

- プロフィール公開項目: 全ログインユーザーが閲覧可能
- 街、建物、ランキング、いいね数: 全ログインユーザーが閲覧可能
- 歩数記録、残高詳細、報酬履歴: 本人のみ

### 書き込み

- プロフィール: 本人のみ
- 歩数と報酬: 本人の操作だけをRPCで受け付ける
- 建物: 街の所有者のみ
- いいね: ログイン中の本人IDをサーバー側で使用する

クライアントから送られた `user_id` を信用せず、認証トークンのユーザーIDを利用する。

## 6. 重要なサーバー処理

### 6.1 `submit_steps(steps)`

1. 認証ユーザーを取得
2. 日本時間の当日を決定
3. 入力範囲を検証
4. 既存値より小さい場合は拒否
5. 当日レコードをupsert
6. 3,000歩以上なら `qualified=true`
7. 更新後の歩数状態を返す

### 6.2 `claim_reward(tier_steps)`

トランザクション内で以下を実施する。

1. ティアが有効か確認
2. 当日の歩数が達しているか確認
3. `reward_claims` の一意制約で二重取得を防止
4. 報酬履歴を追加
5. `profiles` のコイン・チケットを加算
6. 更新後の残高と報酬状態を返す

### 6.3 `place_building(type, x, y)`

トランザクション内で以下を実施する。

1. 建物カタログを取得
2. 人口解放条件を確認
3. 土地開放範囲を確認
4. 固定木・池の座標を確認
5. 配置済み建物との重複を確認
6. コイン・チケット残高を確認
7. 残高を減算
8. 建物を追加
9. 街の人口を再計算・更新
10. 建物、残高、人口を返す

### 6.4 `move_building(building_id, x, y)`

- 所有権を確認
- 移動先のロック・障害物・重複を確認
- 座標だけを更新
- コインと人口は変更しない

### 6.5 `like_town(town_id)`

- 自分の街か確認
- 一意制約で二重いいねを防止
- いいねを追加
- 更新後の件数を返す

### 6.6 ランキング

総人口:

```sql
order by towns.population desc
limit 20
```

今週増えた人口:

- 今週作成された `placed_buildings.population_value` をユーザー別に合計
- 月曜日00:00以降を対象にする
- 値が同じ場合は更新日時など明示した基準で並べる

MVPでは建物売却を実装しないため、週間増加は建築時人口の合計で計算できる。

## 7. 土地開放

- 初期は中央10×10
- 累計または週間目標達成回数に応じて `unlock_level` を更新
- 一度開放した土地は戻さない
- 正確な開放条件は設定テーブルまたは関数内定数へ集約
- フロントエンドへ開放済みマス一覧、または `unlock_level` を返す

ハッカソンデモでは、土地開放済みのシードユーザーを用意する。

## 11. テスト項目

### 報酬

- 未達ティアを取得できない
- 同日同ティアを2回取得できない
- 同時リクエストでも1回分しか増えない
- 歩数を減らして再送信できない

### 建築

- コイン不足で配置できない
- ロック中マスに配置できない
- 木・池の上に配置できない
- 同じマスに2軒置けない
- 他人の街を編集できない
- 支払いと配置が部分的に成功しない

### 交流

- 自分の街へいいねできない
- 同じ街へ二重いいねできない
- 非公開情報が他人へ返らない
- ランキングの人口と街の人口が一致する

## 12. バックエンド完了条件

1. 新規ユーザーのプロフィールと街が作成される
2. 歩数を登録できる
3. 段階報酬を一度だけ受け取れる
4. コインを消費して空きマスに民家を置ける
5. 人口が正しく増える
6. 他人は街を閲覧できるが編集できない
7. いいねとランキングが動作する
8. フロントエンドが契約書どおりのレスポンスを受け取れる

## 13. リスクと対策

| リスク | 対策 |
|---|---|
| 二重報酬 | DB一意制約＋トランザクション |
| コインと建物の不整合 | 購入と配置を1つのRPCにまとめる |
| フロントとの型ずれ | 初日に契約を固定し、レスポンス例を共有 |
| RLS設定漏れ | 別ユーザーで読み書きテストを行う |
| ランキング実装遅延 | Must完了後に追加し、最悪は総人口だけに絞る |
| デモ当日にデータ不足 | 事前に3〜5街のシードデータを作る |
