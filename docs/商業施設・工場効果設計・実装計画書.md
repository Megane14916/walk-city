| 項目 | 内容 |

## 1. 目的

配置済みの商業施設と工場に応じて、歩数同期時の獲得コインを増加させる。

計算と残高更新はSupabase側の同一トランザクションで完結させ、フロントエンドから歩数、建物数、ボーナス率、付与コインを指定できない構造を維持する。また、実バックエンドとmockで同じ計算結果・`appliedBonuses`契約・建物詳細表示を提供する。

本書は次の文書を前提とする。

- 効果値・上限・適用順の正本: [建物効果仕様.md](./建物効果仕様.md)
- 既存APIと型契約: [API計画書.md](./API計画書.md)
- 建物カタログを利用した詳細表示: [建物詳細・表示名変更API設計書.md](./建物詳細・表示名変更API設計書.md)
- 歩数同期の認証・Health取得・エラー契約: [歩数・コイン連携機能DesignDoc.md](./歩数・コイン連携機能DesignDoc.md)

文書間で矛盾する場合、建物効果の値と重複ルールは`建物効果仕様.md`を優先する。

## 2. スコープ

### 2.1 実装するもの

- 商業施設1軒につき10%、最大3軒・30%までの歩数コインボーナス
- 工場1軒につき25%、最大2軒・50%までの歩数コインボーナス
- 商業施設を先に数え、商業施設と工場合計で最大50%とする処理
- ボーナス込みコイン、残高、台帳、同期済み歩数の原子的な更新
- 実際にボーナス率を適用した同期の`appliedBonuses`
- 建物カタログと詳細パネルでの効果説明
- frontend mockでの同一計算
- DB、Edge Function、frontendの単体・契約・結合テスト

### 2.2 実装しないもの

- 建物の配置数自体の制限。4軒目の商業施設や3軒目の工場も購入・配置できるが、超過分は効果を増やさない。
- 過去の歩数報酬への遡及適用
- コイン以外の効果、および公園・病院・農場・役所の実装
- 建物ごとの生産タイマー、コイン回収操作、日次ボーナス上限
- クライアント側での最終コイン計算
- `getBuildingDetail()`のような新規API

## 4. 確定する業務ルール

### 4.1 建物別の効果

| 建物 | 配置数 | 種類別の対象数 | 種類別ボーナス |
| --- | ---: | ---: | ---: |
| 商業施設 | `commercialCount` | `min(commercialCount, 3)` | 対象数 × 10% |
| 工場 | `factoryCount` | `min(factoryCount, 2)` | 対象数 × 25%。ただし合算50%の残枠まで |

計算順序は次のとおりとする。

```text
commercialAmount = min(commercialCount, 3) × 10
factoryPotential = min(factoryCount, 2) × 25
factoryAmount = min(factoryPotential, 50 - commercialAmount)
totalBonusPercent = commercialAmount + factoryAmount
```

これにより`totalBonusPercent`は必ず0〜50の整数となる。

### 4.2 歩数コインの計算

日付ごとの基本コインは既存仕様を維持する。

```text
baseCoins = max(
  0,
  floor(totalSteps / 10) - floor(previousRewardedSteps / 10)
)

awardedCoins = floor(baseCoins × (100 + totalBonusPercent) / 100)
```

割合計算後に1回だけ切り捨てる。建物種類ごとにコインへ変換してから合計してはならない。

例:

| 商業施設 | 工場 | 合算率 | 基本コイン | 獲得コイン | 内訳amount |
| ---: | ---: | ---: | ---: | ---: | --- |
| 0 | 0 | 0% | 100 | 100 | `[]` |
| 1 | 0 | 10% | 100 | 110 | commercial: 10 |
| 3 | 0 | 30% | 100 | 130 | commercial: 30 |
| 4 | 0 | 30% | 100 | 130 | commercial: 30 |
| 0 | 1 | 25% | 100 | 125 | factory: 25 |
| 0 | 2 | 50% | 100 | 150 | factory: 50 |
| 1 | 1 | 35% | 100 | 135 | commercial: 10, factory: 25 |
| 1 | 2 | 50% | 100 | 150 | commercial: 10, factory: 40 |
| 3 | 1 | 50% | 100 | 150 | commercial: 30, factory: 20 |
| 3 | 2 | 50% | 1 | 1 | commercial: 30, factory: 20 |

最後の例では切り捨てにより追加枚数は0だが、基本コインが1以上でボーナス率を計算へ使用しているため`appliedBonuses`は返す。

### 4.3 適用時点

- 同期トランザクションが町をロックした後に確認できる配置済み建物を使用する。
- 建物を配置した後に新しく発生した基本コインだけがボーナス対象となる。
- 建物配置前に精算済みの歩数へ遡って差額を付与しない。
- 建物を移動しても配置数は変わらないため、ボーナス率は変化しない。
- 同じ歩数を再同期して`baseCoins = 0`の場合は、対象建物があっても`coinsAwarded = 0`、`appliedBonuses = []`とする。

## 5. データ設計

### 5.1 効果タイプ

割合であることを型名から判別できるよう、新しい正規の効果タイプを次で統一する。

```text
step_coin_bonus_percent
```

旧mockの`step_coin_bonus_flat`は固定枚数加算を意味する名称で新仕様と不一致のため、互換対象にせず削除する。

### 5.2 `building_effects`の行

| building_type_code | effect_type | value | target_category | scope | stacking_rule | metadata |
| --- | --- | ---: | --- | --- | --- | --- |
| `commercial` | `step_coin_bonus_percent` | 10 | `NULL` | `step_sync` | `commercial_first_combined_cap` | `{"maxEffectiveCount":3,"combinedCapPercent":50,"priority":1}` |
| `factory` | `step_coin_bonus_percent` | 25 | `NULL` | `step_sync` | `commercial_first_combined_cap` | `{"maxEffectiveCount":2,"combinedCapPercent":50,"priority":2}` |

実装では決定的なUUIDを割り当て、migrationと`supabase/seed.sql`で同じID・値を使用する。対象2種類について旧名の効果行が存在する場合は、新行の追加前に明示的に削除または正規化し、同一建物・同一効果タイプが複数行にならないようにする。

`value`は1軒あたりのパーセントポイントである。`metadata`はカタログ説明と監査に利用できる設定表現であり、クライアントが送信する値ではない。

### 5.3 API契約

公開リクエストは変更しない。

```ts
syncSteps(): Promise<ApiResult<StepSyncStatus>>
// Edge Function body: {}
```

成功時の既存型もフィールド追加なしで利用できる。

```ts
type AppliedBonus = {
  sourceBuildingType: 'commercial' | 'factory' | string
  sourceCount: number
  effectType: 'step_coin_bonus_percent' | string
  amount: number
}
```

`sourceCount`は、その種類の実際の配置数とする。種類別上限を超えた建物も含める。`amount`は種類別上限と合算50%上限を適用した後、実際の計算に使用するパーセントポイントとする。

例:

- 商業施設3軒・工場2軒: commercialは`sourceCount: 3, amount: 30`、factoryは`sourceCount: 2, amount: 20`
- 商業施設1軒・工場2軒: commercialは`sourceCount: 1, amount: 10`、factoryは`sourceCount: 2, amount: 40`
- 商業施設4軒・工場3軒: commercialは`sourceCount: 4, amount: 30`、factoryは`sourceCount: 3, amount: 20`

配列順は常に商業施設、工場とし、`amount = 0`の要素は含めない。全日付の`baseCoins`合計が0の場合は必ず空配列とする。

## 6. バックエンド設計

### 6.1 責務分担

```text
sync-health-steps Edge Function
  ├─ JWTから本人を確定
  ├─ Google Healthから当日歩数を取得
  ├─ service_roleでsync_step_rewards()を1回呼ぶ
  └─ DBのsnake_case結果を検証してcamelCaseレスポンスへ変換

sync_step_rewards() DB Function
  ├─ 町行をFOR UPDATEでロック
  ├─ 配置済み商業施設・工場をDBから集計
  ├─ 基本コインとボーナス込みコインを計算
  ├─ daily_step_records・coin_ledger・towns.coinsを同一transactionで更新
  └─ coins_awarded・balance・applied_bonusesを返す
```

最終コイン計算はDB Functionだけが行う。Edge Functionは建物数や率を再計算しない。

### 6.2 ボーナス算出用private関数

`private.calculate_step_coin_bonus(p_town_id uuid)`を追加し、次を返す設計を推奨する。

```json
{
  "total_percent": 50,
  "applied_bonuses": [
    {
      "source_building_type": "commercial",
      "source_count": 3,
      "effect_type": "step_coin_bonus_percent",
      "amount": 30
    },
    {
      "source_building_type": "factory",
      "source_count": 2,
      "effect_type": "step_coin_bonus_percent",
      "amount": 20
    }
  ]
}
```

関数は`placed_buildings`を`town_id`で絞り、`building_effects`の正規行から1軒あたりの率を取得する。種類別上限、商業施設優先、合算上限は正本仕様どおりに適用する。設定行が欠落・重複している場合、または値が商業施設10・工場25の正規値と一致しない場合は、無言で誤精算せず内部エラーとしてトランザクションを失敗させる。

private関数は`SECURITY DEFINER`、`search_path = ''`とし、`public`、`anon`、`authenticated`から実行権限を剥奪する。

### 6.3 `sync_step_rewards()`の変更

町行を`FOR UPDATE`した直後にボーナススナップショットを1回取得し、同一RPC呼び出し内の全レコードへ同じ率を適用する。

レコードごとに次を保持する。

- `base_coins`: 建物効果適用前の今回基本コイン
- `bonus_percent`: 上限適用後の合算率
- `coins_awarded`: ボーナス適用・切り捨て後の付与額
- `applied_bonuses`: 適用内訳。`base_coins = 0`なら空配列

`coin_ledger.metadata`にも少なくとも上記4項目と既存の歩数情報を記録する。これにより、残高だけでなく「どの配置状態のルールで何枚付与したか」を後から監査できる。

トップレベルの`applied_bonuses`は、RPC全体の基本コイン合計が1以上の場合だけ算出済み内訳を返す。現在のEdge Functionは当日1件だけを渡すため、通常はレコード内とトップレベルで同じ内訳になる。

### 6.4 原子性・並行実行・冪等性

- `daily_step_records`、`coin_ledger`、`towns.coins`、返却残高は1つのDBトランザクションで確定する。
- 歩数同期と建物配置はどちらも対象の`towns`行を`FOR UPDATE`する。先にロックした処理が完了した後の配置状態を後続処理が参照する。
- 既存の`rewarded_steps`方式を維持し、同一歩数・減少した歩数の再送では追加付与しない。
- 台帳の`idempotency_key`は既存方式を維持し、リトライで同じ報酬行を追加しない。
- ボーナス率は台帳へ記録済みの結果を後から再計算しない。カタログ設定変更があっても過去台帳は不変とする。

### 6.5 配置RPCへの影響

`place_building()`、`move_building()`の公開入力・レスポンスは変更しない。

- 商業施設・工場は`population_flat`を持たないため、配置時の人口は変化しない。
- 配置成功後の次回歩数同期から効果を持つ。
- 上限を超える配置を`CATALOG_ITEM_DISABLED`等で拒否しない。
- 専用の「効果有効化」列や配置時ボーナスキャッシュは追加しない。配置済み建物が正本である。

## 7. Edge Function設計

`supabase/functions/sync-health-steps/index.ts`はRPCの`applied_bonuses`を次の規則で検証する。

- 配列であること
- 各要素がobjectであること
- `source_building_type`が空でない文字列であること
- `source_count`が1以上のsafe integerであり、その種類の実際の配置数を表すこと
- `effect_type === 'step_coin_bonus_percent'`であること
- `amount`が1〜50のsafe integerであること
- 要素順と合計`amount <= 50`を確認すること
- `coins_awarded = 0`なら空配列であること

検証後、既存の`AppliedBonus`へマッピングする。

```text
source_building_type -> sourceBuildingType
source_count         -> sourceCount
effect_type          -> effectType
amount               -> amount
```

不正な内部レスポンスを受けた場合は、一部だけを採用せず`STEP_REWARD_RESPONSE_INVALID`として既存の`INTERNAL_ERROR`へ変換する。トークン、SQL、Googleレスポンス本文をログへ出さない方針は維持する。

## 8. フロントエンド設計

### 8.1 実API

`StepSyncStatus`と`AppliedBonus`の形はすでに存在するため、新しい公開APIメソッドは不要である。型ガードの既存の非負整数検証に加え、次を契約テストへ追加する。

- commercial/factoryの有効な内訳を受け入れる。
- `amount`合計が50を超えるレスポンスを拒否する。
- 重複したsource、逆順、未知の割合効果をどう扱うかを固定する。MVPではDB契約を厳密にするため拒否を推奨する。
- `coinsAwarded = 0`かつ内訳ありを拒否する。

町の残高更新は従来どおり`coinsAwarded`を手元の残高へ加算せず、サーバーが返した`coinBalance`で置き換える。

### 8.2 建物カタログ・詳細表示

Supabase Serviceの`effectDescription()`へ次を追加する。

```text
step_coin_bonus_percent + value 10
  -> 「歩数同期時の獲得コインを10%増やします」
```

`BuildingDetailPanel`のレイアウトと「人口への効果」カードは変更しない。商業施設・工場の人口効果欄は従来どおり「なし」とし、既存の「効果・説明」一覧へ`BuildingCatalogItem.effects`の説明文を表示する。専用詳細API、主効果カード、上限表示用の新しいUIは追加しない。

### 8.3 同期成功表示

既存の「Nコイン獲得しました」はボーナス込み総額としてそのまま利用できる。追加表示する場合は`appliedBonuses`を表示専用に整形し、たとえば「建物ボーナス +35%（商業施設 +10%、工場 +25%）」とする。残高計算には使用しない。

### 8.4 mock

mockは共有`MockWalkCityStore.getMutableTown().buildings`を集計し、実バックエンドと同じ順序・上限・切り捨てを適用する。

- `MOCK_BUILDING_CATALOG`の商業施設を`step_coin_bonus_percent: 10`へ修正する。
- 工場へ`step_coin_bonus_percent: 25`を追加する。
- `createMockStepSyncApi()`は基本コインを算出後、配置数から合算率を算出する。
- mockの`appliedBonuses`も実APIと同じ`sourceCount`定義と順序で返す。
- `reset()`後は初期町・初期報酬状態だけでなく、建物配置に基づく率も初期状態へ戻る。

## 10. テスト計画

### 10.1 DBカタログ

- 正規の効果行が商業施設・工場に各1件だけ存在する。
- `value`が10、25、`effect_type`が`step_coin_bonus_percent`である。
- カタログViewが効果行を構造化して返す。
- authenticatedは効果を読めるが、追加・更新・削除できない。

### 10.2 DB精算

最低限、次の配置パターンをパラメータ化して検証する。

| 商業施設 | 工場 | 期待合算率 | 期待内訳 |
| ---: | ---: | ---: | --- |
| 0 | 0 | 0 | `[]` |
| 1 | 0 | 10 | C: count 1 / amount 10 |
| 3 | 0 | 30 | C: count 3 / amount 30 |
| 4 | 0 | 30 | C: count 4 / amount 30 |
| 0 | 1 | 25 | F: count 1 / amount 25 |
| 0 | 2 | 50 | F: count 2 / amount 50 |
| 0 | 3 | 50 | F: count 3 / amount 50 |
| 1 | 1 | 35 | C: 10, F: 25 |
| 1 | 2 | 50 | C: count 1 / 10, F: count 2 / 40 |
| 2 | 2 | 50 | C: count 2 / 20, F: count 2 / 30 |
| 3 | 1 | 50 | C: count 3 / 30, F: count 1 / 20 |
| 3 | 2 | 50 | C: count 3 / 30, F: count 2 / 20 |

追加で次を確認する。

- 基本コイン1、率10%で獲得1となり、内訳は返る。
- 基本コイン3、率35%で獲得4となる。
- `baseCoins = 0`では内訳が空で台帳行を作らない。
- 同じ歩数の再送、低い歩数の送信で追加付与しない。
- 建物配置前に一度同期し、配置後に増えた歩数だけへ効果が付く。
- 同期と配置の並行実行で、どちらか一方の一貫した配置状態だけが採用される。
- `coin_ledger.amount`合計、`towns.coins`、レスポンス残高が一致する。
- 台帳metadataへ基本額、率、内訳が保存される。
- 設定行欠落・重複・不正値では残高や同期済み歩数を部分更新しない。

### 10.3 Edge Function

- RPCのsnake_case内訳を既存のcamelCase型へ正しく変換する。

## 13. 実装時の注意点

- `sync_step_rewards()`はservice_role専用のまま維持し、authenticatedへ直接公開しない。
- `building_effects.metadata`やフロントエンドのカタログをそのまま信用してコインを付与しない。DB内の検証済み設定と配置済み建物だけを使用する。
- `coinsAwarded`は基本額ではなくボーナス込み総付与額である。
- UIは`coinBalance`を正として残高を置換し、`coinsAwarded`を再加算しない。
- 既存migrationを編集すると適用済み環境との差分が消えるため、新規migrationを追加する。
- 効果値の将来変更ではカタログ行、精算テスト、mock fixtureを同じ変更単位で更新する。

## 14. Phase 1で確定した事項

1. 効果タイプ名を`step_coin_bonus_percent`へ統一し、旧mockの`step_coin_bonus_flat`を廃止する。
2. `sourceCount`はその種類の実際の配置数とし、上限超過分も含める。`amount`は上限適用後の有効ボーナス率とする。
3. 建物詳細のレイアウトと固定「人口への効果」欄は変更しない。
4. 商業施設は最大3軒分、工場は最大2軒分、商業施設優先で合計最大50%とする。

以上により、Phase 1で未決定の仕様項目はない。
