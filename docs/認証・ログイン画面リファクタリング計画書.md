## 1. 目的

現在 `frontend/src/App.tsx` に集中しているログイン、Google Health 連携、歩数表示、モック操作の責務を分離し、フロントエンド設計書が定める Page、Feature、Service、Mock の依存方向へ整理する。

本リファクタリングでは、次を達成する。

- 認証 API とモック API が同じ公開インターフェースを使用する。
- モック実装を `frontend/src/mocks/` に集約する。
- セッション復元と認証状態をアプリ全体で一元管理する。
- ログイン画面と Google Health 連携 UI を `frontend/src/App.tsx` から分離する。
- URL と Page の対応を `app/router.tsx` に集約する。
- `App.css` のスタイルを Tailwind CSS へ移行し、同ファイルを削除する。
- ログインと Google Health の追加認可を別操作として維持する。

## 4. 現状の課題

### 4.1 `App.tsx` の責務過多

現在の `frontend/src/App.tsx` は次の責務を同時に持っている。

- セッション復元
- Google ログイン
- Google Health 連携・解除
- 日次歩数取得
- ログアウト
- ログイン、未連携、接続済みの全画面表示
- モックのエラー注入とリセット
- 日付、タイムゾーン、歩数目標の決定
- 画面装飾用コンポーネント

Page、Feature Hook、Feature Service、Mock Service の責務が分離されておらず、実 API への切り替えと画面単位のテストが難しい。

### 4.2 モックへの直接依存

`App.tsx`、`RequireAuth`、`TownPage`、テストが `features/auth/api` から `mockGoogleIntegrationApi` を直接 import している。

この状態ではコンポーネントが実装種別を知っており、「環境変数または Provider 生成時に実サービスとモックを切り替える」「コンポーネント内で mock 分岐を持たない」という設計に反する。

### 4.3 認証状態の重複取得

`App.tsx` と `RequireAuth` がそれぞれ `getState()` を実行している。Page や Guard が個別にセッションを復元すると、リロード時のちらつき、余分な待機、画面ごとの状態不整合が発生する。

### 4.4 型定義の重複

`ApiResult` とエラーコードが `features/auth/api/google-integration-api.ts` と `types/common.ts` に重複している。共通契約の変更時に両方がずれる可能性がある。

### 4.5 ルーティングの不足

- ログイン成功後に Google Health 連携画面専用のルートへ遷移する構成がない。
- 設計書にある `/town/:userId` が `router.tsx` と `paths.ts` にない。
- `/auth/callback` を専用ルートにするかが未決定である。
- ログイン成功、ログアウト成功時の replace 遷移が共通化されていない。

### 4.6 CSS の配置

ログイン画面のスタイルが `App.css` に集約され、Tailwind CSS を基本とする実装規約と一致していない。疑似要素、メディアクエリ、アニメーションを含むため、単純な class の置換ではなく装飾要素の構造も整理する必要がある。

## 5. 設計方針

### 5.1 依存方向

```text
Route / Page
    ↓
Feature Component
    ↓
Feature Hook / Auth Context
    ↓
Feature Service Interface
    ↓
Supabase Service または Mock Service
```

Page と Feature Component は、選択されている API が実 API かモックかを判断しない。

### 5.2 ログインと Health 連携の分離

- Google ログインでは本人識別に必要なスコープだけを要求する。
- Google Health の歩数読み取り認可はログイン後の別操作とする。
- Health 連携を拒否・スキップしてもログイン済み機能を利用可能にする。
- ログアウトしても Health 連携情報は解除しない。
- Health 連携解除では Supabase セッションを終了しない。

### 5.3 画面とURL

ログイン後も現在と同じ順序で Google Health 連携 UI を表示するため、認証必須の `/health/connect` を追加する。関連する画面一覧とルート定義は、本実装と同じ変更内で更新する。

| Path | Page | 認証 | 動作 |
|---|---|---|---|
| `/login` | `LoginPage` | 不要 | ログイン成功後は `/health/connect` へ replace |
| `/health/connect` | `HealthConnectionPage` | 必須 | Google Health 連携、スキップ、接続完了を表示 |
| `/` | `TownPage` | 必須 | 自分の街とダッシュボードを表示 |
| `/town/:userId` | `TownPage` | 必須 | 他ユーザーの街を閲覧 |
| `/ranking` | `RankingPage` | 必須 | 人口ランキング |
| `/users/:userId` | `UserPage` | 必須 | ユーザー公開情報 |
| `/auth/callback` | `AuthCallbackPage` | 不要 | 採用する Supabase フローで必要な場合のみ追加 |

画面遷移は次のとおりとする。

```text
/login
  Googleログイン
       ↓
/health/connect
  Google Health連携画面
       ├─ 連携する → 接続完了表示 → /
       └─ 今は連携しない          → /
                                      ↓
                                  TownPage
```

`app/routes/HealthConnectionPage.tsx` は URL、Route Guard、連携完了・スキップ後の遷移を担当する。実際の連携表示と操作は `features/health/components/HealthConnectionPanel.tsx` と `features/health/hooks/useHealthConnection.ts` に置く。

`app/routes/TownPage.tsx` には初回セットアップ用の Google Health 連携画面を組み込まない。TownPage は街、Map、ダッシュボードの表示に専念する。ただし、未連携状態でも `/` へ直接移動でき、「今は連携しない」を選択したユーザーがゲームを利用できる状態は維持する。

## 7. 実装計画

### Phase 1: 契約型の整理

1. `ApiResult<T>`、`ApiError`、`ApiErrorCode` の正を `types/common.ts` に統一する。
2. `AuthSession`、`GoogleIntegrationState` など、認証機能固有の型を `features/auth/types.ts` へ移す。
3. Health 画面固有の状態型を `features/health/types.ts` へ分離する。
4. `GoogleIntegrationApi` が共通の `ApiResult<T>` を返すようにする。
5. 現在の `getState()` を設計書の名称である `getGoogleIntegrationState()` へ統一する。
6. UI とテストの import を一度に更新する。

### Phase 2: モックの移動

1. `mock-google-integration-api.ts` を `mocks/services/google-integration.ts` へ移す。
2. モックユーザー、初期 Health 状態、日別歩数を `mocks/data/` へ移す。
3. 疑似遅延、操作単位のエラー注入、歩数変更、リセット機能を維持する。
4. `permission_required` を含む接続状態を再現できるようにする。
5. テストでは `now`、タイムゾーン、対象日を注入し、実行日によって結果が変わらないようにする。
6. モックの barrel export を `mocks/services/index.ts` に集約する。

### Phase 3: API実装の注入

1. `ApiProvider` で認証・Health Service を公開する。
2. `VITE_API_MODE=mock|supabase` などの環境変数を起動時に検証する。
3. mock モードでは `mocks/services/google-integration.ts` を生成する。
4. supabase モードでは `features/auth/services/google-integration.ts` を生成する。
5. コンポーネントから環境変数やモック実装を直接参照しない。
6. Supabase 実装を行う場合は `@supabase/supabase-js` と `lib/supabase.ts` を追加する。

実 API の追加には、バックエンド担当と次を確認する必要がある。

- Supabase URL と公開用 anon key の環境変数名
- OAuth の `redirectTo`
- Google Health 連携開始・解除用 Edge Function 名
- `getGoogleIntegrationState()` の取得方法
- エラーコードと `ApiResult<T>` のマッピング
- `/auth/callback` 専用ルートの要否

### Phase 4: Auth Provider

1. `AuthProvider` がアプリ起動時に一度だけセッションを復元する。
2. 次の認証状態を提供する。

```ts
type AuthState =
  | { status: 'initializing' }
  | { status: 'authenticated'; session: AuthSession }
  | { status: 'unauthenticated' }
  | { status: 'error'; error: ApiError }
```

3. `signInWithGoogle()`、`signOut()`、再試行を Provider または `useAuth()` に集約する。
4. 実 API では Supabase Auth の状態変更を購読し、破棄時に解除する。
5. ログアウト時に認証依存キャッシュと表示中のユーザーデータを破棄する。
6. `RequireAuth` は `useAuth()` の状態だけを使用する。

### Phase 5: ログイン画面の分離

1. 未ログイン表示を `app/routes/LoginPage.tsx` へ移す。
2. `LoginButton` と認証操作を `features/auth` へ分離する。
3. セッション確認中、未ログイン、Google への遷移中、エラーを明示する。
4. ログイン成功後は `/health/connect` へ replace 遷移する。
5. ログインボタンの連打を防止する。
6. OAuth キャンセル・一般エラーから再試行できるようにする。
7. ログイン画面では Health スコープを要求しないことを表示する。

### Phase 6: Google Health 連携UIの分離

1. `app/routes/HealthConnectionPage.tsx` を追加し、認証必須の `/health/connect` に割り当てる。
2. 未連携、接続済み、再同意が必要な状態を `features/health` で表示する。
3. `startGoogleHealthConnection()` の結果を次のように処理する。
   - `next: 'redirect'`: Service が返した URL へ遷移する。
   - `next: 'connected'`: 外部遷移せず状態を更新する。
4. ログイン成功直後は、接続状態にかかわらず `/health/connect` で現在と同等の Health 連携・接続完了 UI を表示する。
5. 「今は連携しない」で `/` へ遷移し、ゲーム画面の利用を継続できるようにする。
6. 連携完了後は同じルート内で接続完了を表示し、ユーザー操作で `/` へ遷移できるようにする。
7. 連携解除には影響を説明する確認操作を挟む。
8. `permission_required` では再同意ボタンを表示する。
9. TownPage に初回セットアップ用の Health 連携 UI を重複配置しない。

### Phase 7: ルーティングの修正

1. `/login` に `LoginPage` を割り当て、現在の `App` 直接割り当てを削除する。
2. `/health/connect` に `HealthConnectionPage` を割り当て、認証必須にする。
3. `app/App.tsx` で Provider 群と Router を組み合わせる。
4. 未認証ユーザーが `/health/connect` またはその他の保護ルートを開いた場合は `/login` へ replace 遷移する。
5. ログイン成功後と、認証済みユーザーが `/login` を開いた場合は `/health/connect` へ replace 遷移する。
6. Health 連携完了またはスキップ後は `/` へ遷移する。
7. `paths.ts` に `/health/connect`、`/town/:userId` とリンク生成関数を追加する。
8. OAuth の方式確定後、必要なら `/auth/callback` を追加し、セッション復元後は `/health/connect` へ遷移する。
9. `router.tsx` にはデータ取得やモック操作を置かない。

### Phase 8: Tailwind CSSへの移行

1. `App.css` のレイアウト、色、余白、文字、レスポンシブ指定を Tailwind utility class へ変換する。
2. 疑似要素で作られた街、雲、木、人物は、Tailwind の `before:` / `after:` または明示的な装飾要素で再構成する。
3. `@media` を Tailwind の responsive variant へ移行する。
4. `@keyframes` は Tailwind の animation utility またはトランジションへ置き換える。
5. `prefers-reduced-motion` の挙動を `motion-reduce:` で維持する。
6. 実行時の歩数割合が必要な `conic-gradient` だけはインライン style を許容する。
7. `App.css` の import とファイル本体を削除する。
8. `index.css` は Tailwind import とアプリ全体の最低限のリセットだけを残す。

### Phase 9: テストと文書更新

1. Mock Google Integration Service の単体テストを追加する。
2. Auth Provider と `useAuth()` の状態遷移をテストする。
3. `LoginPage` の初期化、成功、失敗、二重送信防止をテストする。
4. Health 未連携、接続済み、権限不足、OAuth キャンセルをテストする。
5. 未認証・認証済み双方のルート遷移をテストする。
6. `/town/:userId` と未定義ルートをテストする。
7. PC、タブレット、スマートフォン幅でログイン画面を確認する。
8. `npm test`、`npm run lint`、`npm run build` を実行する。
9. 移動後のファイルパス、採用済みルーティングライブラリ、確定した callback 方針を関連文書へ反映する。

## 8. テスト観点

### 8.1 認証

- 初回セッション復元中にログインボタンが表示されない。
- 未ログイン状態から Google ログインを開始できる。
- ログインボタンを連打できない。
- ログイン成功後に `/health/connect` へ replace 遷移する。
- 認証済みで `/login` を開くと `/health/connect` へ replace 遷移する。
- 未認証で `/health/connect` を開くと `/login` へ replace 遷移する。
- ログアウト後に `/login` へ replace 遷移する。
- セッション復元失敗後に再試行できる。

### 8.2 Google Health

- 未ログインでは Health 連携を開始できない。
- ログイン成功直後に `/health/connect` の Health 連携 UI が表示される。
- 未連携時に連携ボタンが表示される。
- `connected` で同期日時と解除操作が表示される。
- `permission_required` で再同意を案内する。
- OAuth キャンセル後もゲーム利用を継続できる。
- ログアウトだけでは保存済み Health 連携を解除しない。
- Health 連携解除後もログイン状態を維持する。
- 実 API の redirect とモックの即時接続を同じ UI で処理できる。
- 連携完了または「今は連携しない」の後に `/` へ遷移できる。
- TownPage に初回セットアップ用の Health 連携画面が重複表示されない。

### 8.3 モック

- 疑似遅延を設定できる。
- 操作単位でエラーを注入・解除できる。
- 日別歩数を変更できる。
- リセット後に初期状態へ戻る。
- 固定時計を渡したテストが実行日やローカルタイムゾーンに依存しない。

### 8.4 UI

- 320px 以上の画面幅で横スクロールを発生させない。
- キーボード操作でログイン、連携、スキップ、再試行ができる。
- ローディングとエラーが `aria-live` などで通知される。
- reduced-motion 環境で不要なアニメーションが抑制される。
- `App.css` を削除しても既存の主要な見た目を維持する。

## 9. 現在確認されているテスト状態

Phase 9 完了時点のフロントエンド検証結果は次のとおりである。

| コマンド | 結果 |
|---|---|
| `npm run lint` | 成功 |
| `npm run build` | 成功 |
| `npm test` | 88件すべて成功 |

計画作成時に確認されていた次の失敗は解消した。

1. 未認証のランキングルートからログイン画面へ遷移するテストが、モック遅延と重複した状態復元の影響を受けて不安定である。
2. Health 接続後の歩数表示テストで、固定日時、Sydney の日付、`stepsByDate` のキーが一致していない。

Auth Provider による一度だけのセッション復元と、時計・対象日の明示的注入によって修正した。

PC、タブレット、スマートフォン向けのTailwind生成CSS、320pxの最小幅、レスポンシブvariant、`prefers-reduced-motion`は確認済みである。実ブラウザの接続が利用できなかったため、画面幅ごとの目視確認とスクリーンショット比較は未実施である。

## 10. 実装で解消したドキュメントとの不一致

### 10.1 モックの配置

モック実装を `mocks/services/` へ移し、`Google認証機能DesignDoc.md` の実装ファイル例と import 例を更新した。`features/auth/api/` には公開インターフェースだけを残した。

### 10.2 ルーティングライブラリ

`react-router-dom` の採用を関連文書へ反映した。

### 10.3 公開街ルート

`/town/:userId` とパス生成関数を追加し、公開街では `getPublicTown(userId)` を使用するようにした。

### 10.4 ログイン画面の遷移

`/health/connect` と `HealthConnectionPage` を追加し、ログイン成功後の遷移規則を関連文書へ反映した。

### 10.5 セッション復元

セッション復元を `AuthProvider` に集約し、`RequireAuth` と各Pageは `useAuth()` の状態だけを使用するようにした。

### 10.6 API名と型

- API 名を `getGoogleIntegrationState()` に統一した。
- `ApiResult<T>` と `ApiError` の正を `types/common.ts` に統一した。
- `GoogleIntegrationErrorCode` は共通 `ApiErrorCode` から抽出する型に変更した。

### 10.7 歩数同期

API 設計はゲーム上の歩数精算に `syncSteps()` を使用し、フロントエンドから歩数を送らない方針である。現行の接続済み画面は `getDailySteps()` を「歩数更新」操作として使用している。

後続の歩数・コイン連携実装で、接続済み画面の同期操作を Town/Dashboard 側へ統合し、ゲーム上の精算は `syncSteps()` を正とした。`getDailySteps()` は移行期間の初期表示専用であり、報酬や残高更新には使用しない。

### 10.8 タイムゾーン

ゲーム上の歩数精算について、初期リリースの日付境界を `Asia/Tokyo` に固定した。`syncSteps()` ではクライアントから日付やタイムゾーンを送らず、レスポンスの `date` と `timezone` を正とする。

初期表示に使う `getDailySteps()` も `Asia/Tokyo` に統一する。`getDashboard()` は使用せず、表示用取得と報酬精算の責務を分けたまま同じ日付境界を使用する。

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| ファイル移動中に import が壊れる | 移動と全 import 更新を同一変更内で行う |
| Provider 導入でルーターのテストが複雑になる | テスト用 Provider factory と latency 0 のサービスを用意する |
| 実 API とモックの状態遷移が異なる | 同じインターフェースと契約テストを使用する |
| OAuth リダイレクト後に元の状態が残る | callback 方針を確定し、セッションを正として再取得する |
| Tailwind 移行でデザインが崩れる | 画面幅ごとの手動確認と既存UIのスクリーンショット比較を行う |
| mock 専用操作が本番へ露出する | 開発モードかつ mock モードでのみ構成する |
| Health 連携画面から先へ進めなくなる | 「今は連携しない」で `/` へ遷移できることをテストする |
